01
The Problem
What problem is this
actually solving?

The standard library gave us primitives. It never gave us a model. So we all built our own — and none of them compose.

The problem, concretely

Four years ago I built an async I/O scheduler with a common interface backed by two implementations: io_uring in production, and a thread pool fallback for environments where io_uring isn't available. It has cancellation via stop tokens.

This was standard practice — every shop with serious async needs built some version of it. And every one of those systems, mine included, hits the same structural ceiling:

  • ✗No two of them compose. Work pipelines are ad-hoc plumbing; integrating another team's async domain means writing a custom bridge — every time.
  • ✗None of them share a vocabulary. My interface is mine, Asio's is Asio's — no generic algorithm can span them.
  • ✗Each one invents error and cancellation propagation. Exceptions here, error_codes there, silent drops somewhere else.

These aren't design mistakes — they're the ceiling any single-team library hits, because composing across teams needs a vocabulary everyone shares, and only a standard can provide one. P2300 takes the instinct we all had — separate computation from execution context — and makes it universal.

The prior art — what every large C++ shop built:

  • Team A uses Boost.Asio with callbacks
  • Team B uses hand-rolled thread pool + futures
  • Team C wrote a coroutine framework
  • You wrote an io_uring scheduler
  • None of these compose with each other
  • Each has its own error propagation story
  • Each has its own cancellation story — or doesn't

P2300's pitch: a vocabulary layer that all of these can speak. Work from any source composable with any other source, using generic algorithms.

Delivery: the ✗s are coordination failures, not engineering failures — no amount of skill fixes them from inside one team, because they require everyone else to agree on a vocabulary. Land that sentence before advancing; it's the whole reason the fix is a standard and not a better in-house library. Your system stays on stage as the exemplar of standard practice, not the patient.

Why std::future isn't the model — and what is

What's broken

  • ✗No continuations. .then() was proposed in 2013 (N3721), shipped in the Concurrency TS in 2016, and never merged into the IS — chaining means blocking on .get() or spawning another thread.
  • ✗No cancellation, no readiness callback. You poll in a loop or you block.
  • ✗No scheduler control. std::async gives you one bit — new thread or lazy — and under the default policy even that bit is implementation-defined. You can never say which context.
  • ✗Blocking fan-in, one error channel. Join N futures serially. The only built-in failure path is set_exception, so an error_code I/O layer either throws system_error per errno, or smuggles results through expected<> and leaves the error channel unused.

What a real model needs

  • ✓Composable continuations. Chain, fan-out, fan-in — one syntax regardless of what's underneath.
  • ✓First-class cancellation. Stopped is its own completion channel, not an exception in disguise.
  • ✓Scheduler-agnostic. Thread pool, GPU, io_uring ring, interrupt handler — the computation shouldn't care.
  • ✓Uniform completion. Value / error / stopped, propagated automatically through the chain.

Each ✗ maps to the ✓ beside it. Two more requirements we'll meet in the model section: zero overhead on the default path (allocation opts in, never sneaks in) and structured lifetimes — the model is shaped so child work completes before its parent scope exits.

Be precise if challenged on the error point — promise<expected<T, error_code>> obviously works, so don't say futures are "incompatible" with error_code I/O. The claim is that there's exactly one built-in failure channel and it's an exception: either you throw system_error for routine errno values, or you push failure into the value channel and the type stops telling anyone that failure is possible. And .get() rethrows wherever you happened to join, not where the error occurred. Detail dropped from the slide: futures always heap-allocate shared state, even for trivial work. launch::deferred is laziness without value — runs on the retrieving thread, can't target a scheduler, can't compose. jthread fixes thread lifetime but is still a thread: no when_all, no error propagation out. The coroutine ecosystem's failure modes are different — next slide.

What about coroutines?

C++20 gave us the coroutine mechanism — co_await and co_return — but almost no library to use it with. The problems below aren't with coroutines themselves; they're with the missing infrastructure around them.

  • ✗No standard scheduler. Every coroutine library — cppcoro, Asio, folly, libunifex — independently reinvented where coroutines run and how they're scheduled.
  • ✗No structured cancellation. Cancelling a coroutine chain requires library support — there's nothing in the language to propagate stop signals.
  • ✗Fan-out is awkward. co_await is sequential by nature. Concurrent fan-out requires library primitives that don't exist in the standard.
  • ✗No scheduler portability. A coroutine written against Asio's executor doesn't compose with one written against a custom io_uring scheduler.

The good news: they interoperate

P2300 deliberately treats coroutines as a first-class citizen. You don't have to choose.

// Name the sender, then await it.
exec::task<int> my_coroutine() {
    auto doubled = stdexec::just(42)
                 | stdexec::then([](int x) { return x * 2; });

    co_return co_await std::move(doubled);
}

// A coroutine task is itself a sender
auto work = stdexec::when_all(my_coroutine(),  // sender ✓
                              other_work());   // sender ✓

Gotcha: co_await binds tighter than |. co_await s | then(f) awaits s and pipes the result into then. Parenthesize, or name it first.

Use co_await for sequential async steps where it reads well. Use sender algorithms for parallelism, fan-out, and scheduler control. Compose them freely.

The gotcha is worth 15 seconds: co_await is a unary-expression operator, so it outranks the pipe. The failure is usually a confusing type error, occasionally something that compiles and is wrong. Also note the std::move — these are single-shot senders and connecting from an lvalue is the wrong habit. Framing line before advancing: coroutines and std::future have DIFFERENT failure modes — futures fail at composability; the coroutine ecosystem fails at parallelism, cancellation, and portability. P2300 provides the missing infrastructure and treats coroutines as a first-class citizen in the process.

The Model
Three abstractions.
One vocabulary.

Scheduler · Sender · Receiver — and why as a user you mostly only deal with one of them.

The vocabulary — and why senders are lazy

📍 Scheduler — a handle to an execution context. Where does work run? Your io_uring ring becomes one.

📦 Sender — a lazy description of async work. You spend ~95% of your time here.

📬 Receiver — a generalized callback (value / error / stopped). You almost never write one — but you'll call into one the moment you wrap your own I/O.

// Nothing runs yet. This is just a description.
auto work =
    stdexec::schedule(sched)           // start on scheduler
    | stdexec::then([] { return compute_something(); })
    | stdexec::then([](auto r) { return transform(r); });

// Work STARTS here. Calling thread blocks until done.
auto [value] = stdexec::sync_wait(work).value();
// Swap the scheduler — pipeline logic is unchanged.
auto cpu_work  = pipeline(thread_pool_sched);
auto gpu_work  = pipeline(cuda_stream_sched);
auto ring_work = pipeline(io_uring_sched);  // your scheduler!

Pipeline built left-to-right with |. Each step returns a new sender — nothing executes until a consumer connects and starts it.

Senders are values. Store them, pass them to functions, modify them before running. That is what composability actually means.

If asked "so when WOULD I write a receiver?": separate consuming one from defining one. Wrapping I/O — the rest of this talk — means writing a sender and an operation state; connect hands you a receiver and you call set_value / set_error / set_stopped on it. You never define the type. You define a receiver type only when you write a sender ALGORITHM (then, or a custom adaptor), a custom consumer (your own sync_wait, spawning into your own scope), or type erasure like any_sender_of. If you're writing an adaptor you're extending the framework rather than using it — different talk. Two minutes, not six. Read the three boxes in one breath — this room can define scheduler and receiver without help; the only lines that earn time are "your ring becomes a scheduler" and "you almost never write a receiver." Then land the hook: if your scheduler is an io_uring ring, pipeline(ring_sched) routes all that work through your ring and the computation logic is unchanged. That's the whole promise of the talk in one line.

Three ways work completes — all uniform

set_value(args...)
Success. Zero or more values forwarded downstream — a single completion can carry several independent results, which std::future cannot express at all.

set_error(err)
Failure. exception_ptr, error_code, or any type. Propagates automatically through the chain.

set_stopped()
Cancellation. Structured and explicit — not an exception, not an error code.

// Errors propagate automatically — no try/catch at every step
auto pipeline =
    async_read(sched, fd, buf)         // might set_error()
    | stdexec::then([](Buffer b) {
          return parse(b);               // only runs if no error
      })
    | stdexec::upon_error([](auto err) {   // error_code AND exception_ptr
          log_error(err);
          return fallback_value();        // recover and continue
      })
    | stdexec::upon_stopped([] {
          cleanup();
          return fallback_value();        // same type as the value path
      });

Why auto err: then adds set_error_t(exception_ptr) unless the callable is noexcept — a handler taking only error_code won't compile.

One uniform completion story — no more per-library mix of exceptions, error codes, and silent failures.

Say, don't show: the multi-value capability is why sync_wait always returns optional<tuple<...>> even for one value — the optional is empty on cancellation, the tuple carries all values. when_all uses this to deliver one result per branch in a single completion. Why upon_stopped returns a value here: a void handler would give the sender two distinct set_value signatures — set_value(T) from the happy path and set_value() from the stopped path. That's legal, but sync_wait wants a single value completion signature, so the obvious-looking void version fails to compile at the consumer. Mention only if someone asks; it's a good "you've clearly written this" beat.

"Isn't then just the callback?"

The first objection I promised to come back to. Same operation, both ways.

The callback you'd have written

struct ctx { char* buf; };   // heap; free it yourself

void on_read(int result, void* p) {
    auto* c = static_cast<ctx*>(p);
    if (result < 0) { /* on whose thread?
                             report to whom? */ }
    else process(c->buf, result);
    delete c;
}

async_read(fd, buf, n, &on_read, new ctx{buf});
// nothing here to name, store, or compose

The sender

auto work = async_read(fd, buf, n)
          | stdexec::then(process);

// ...and `work` is a value:
stdexec::sync_wait(std::move(work));   // run here
scope.spawn(std::move(work));          // or there
co_await std::move(work);              // or await
stdexec::when_all(std::move(work),      // or fan out
                   other_work());

The consumer decides how it runs — not the algorithm. Same pipeline, four different executions, none of which async_read had to know about.

Where does the stop token go? There's one parameter left and it's void*. Same question for "which context does process run on?" and "who owns buf until completion?"

A callback is a function you give away. You hand it to async_read at the call site and it's gone. A sender is a value you keep.

The concession, and it's real: for one step, no errors, no cancellation, no fan-out — they are equivalent, and the callback version is less code. The value shows up at the second step, and at every seam between two libraries.

Concede the true half first, in exactly these words: "he's right that process gets invoked much like a callback, and right that this compiles down to something callback-shaped." Then turn it — the difference isn't the step, it's what you're holding. Walk the right column top to bottom slowly. Four consumers, one pipeline, and async_read knew about none of them. That's the entire argument and it's visual — let it land before you say anything else. The void* line usually gets the laugh and it's the most concrete point on the slide: every capability the model adds needs somewhere to live, and the callback signature has exactly one slot left. Read the concession box like you mean it — for a single step the objection is correct, and saying so is what earns you the rest. If someone pushes on error handling: point back at the previous slide. result < 0 on the library's thread has nowhere to go; set_error travels the chain to a consumer that chose to be there.

"Just do it in a destructor"

And the second objection — take it at face value and write the program it implies.

~BufferWriter() {
    // flush what's still pending before we go
    for (auto& b : pending_) {
        ::write(fd_, b.data(), b.size());
    }
}
  • ✗It has no idea why it's running. Success, error, cancelled — same code, no parameter. uncaught_exceptions() is the only signal, and cancellation isn't an exception: to a destructor, a cancelled operation is indistinguishable from a successful one.
  • ✗So it can't know whether flushing is even correct. After a failed or cancelled write, pending_ may hold a partial record. Writing it corrupts the file; dropping it loses data. It must guess.
  • ✗And it can't report either outcome — destructors can't throw, so a failed flush is silent.
  • ✗A blocking write on the shutdown path, with no timeout. Route it through your async layer and you're blocking on a context being torn down — the classic shutdown deadlock.
  • ✗And shutdown can't be parallelised. Objects are destroyed one at a time, in reverse order of construction — block scope, members, statics alike. Ten writers with 50 ms of I/O each is 500 ms of serial teardown that when_all would have finished in 50.

Three channels collapse into one. Everything the model keeps separate — value, error, stopped — arrives at ~T() as the same call. And the language forbids the fix: neither a constructor nor a destructor may be a coroutine ([class.ctor.general], [class.dtor]).

C++26 already hit this wall. counting_scope's cleanup — join() — is async, so its synchronous destructor calls terminate() if you forgot. A standard type whose correctness depends on remembering an idiom: the C-style problem RAII was invented to kill.

So async RAII is being built in the sender domain. Shoop's P2849, now Leahy's P3955 (Jan 2026) — implemented on stdexec, with an io_uring example that closes sockets via IORING_OP_CLOSE. On your platform even close is async.

The claim was that none of this matters. But every codebase that believes it ends up with a hand-rolled shutdown sequence, a comment explaining the ordering, and a bug nobody can reproduce.

This is the one slide where you're allowed to be pointed — but aim it at the claim, never the person. The factual core: async cleanup is not expressible as a destructor, full stop. That isn't an opinion about style, it's a property of the language. This answers the destructor objection, NOT the syntactic-sugar one — they came from different people and they are different claims. The sugar objection was answered on the previous slide; say so if anyone conflates them. The line to land here: "a destructor cannot tell you why it's running, and in an async system it cannot even see cancellation — so it has to guess whether flushing is the right thing to do." If someone raises std::uncaught_exceptions(): that's the scope_fail / scope_success mechanism and it only detects exception unwinding. set_stopped isn't an exception, so it reads zero on the cancellation path — the destructor concludes success. That's the whole argument in one sentence. Point back at the previous slide: the three completion channels they are still looking at collapse to a single unparameterised call here. The structural echo does more work than any bullet — that is the reason this slide sits where it does. Say the concession out loud — it was a box here and it still matters. "If your process only ever exits by abort(), every error is genuinely fatal, and nothing needs flushing, then they're right and you don't need any of this. Know which system you have before you argue about it." Without that sentence you lose everyone who walked in agreeing with the objection. On the serial point, if pressed for precision: the rule is reverse order of construction, sequentially — it isn't only lexical blocks, it covers class members and static destruction too. And there's no escape: you could have each destructor fire off async work and not wait, but then you've abandoned the guarantee and you're back to fire-and-forget. To be correct you must block, and blocking is serial. The terminate behaviour is identical in simple_counting_scope — same rule, both types: terminate unless joined, unused, or unused-and-closed. Naming either one is fine; just don't switch between them mid-talk. Dropped for space, use if asked: destruction order is lexical scope order, not dependency order, so the ring the flush needs may already be gone. The generous framing, and the true one: wanting cleanup in a destructor is wanting async RAII. That instinct is right and the committee agreed — P1662 tried to put it in the language in 2019 and failed. What shipped instead is the library version, in the sender domain. So the objection isn't an argument against senders; it's a request for something senders provide. P3955R0 "It's Scopes All the Way Down" (Leahy, 14 Jan 2026) is the paper: enter-scope senders that yield exit-scope senders, with within / enter_scopes / nest_scopes / lifetime, continuing Kirk Shoop's P2849 with his permission. Implemented on stdexec, not yet published. He's presenting "Implementing Async RAII" at CppCon 2026 — mention that, it's a genuine service to the room. If you want one more example: the paper reformulates an async mutex as acquire() returning an enter-scope sender, which lets you take three mutexes in parallel — impossible with the wrap-a-sender shape. VERIFY: P3955 is R0 and pre-LEWG; say "proposed", never "coming in C++29." Have the AV example ready if pressed: sensor timeouts, mode transitions, watchdog-triggered subsystem restarts, and simulation runs that stop early are all cancellation that isn't process exit. But don't lead with domain specifics — half the room isn't in your domain. Read the concession box slowly and mean it. If it sounds grudging you lose everyone who came in agreeing with your colleagues, and they're the people you're actually here for.

The API
Writing sender code
in practice

The algorithms you'll use every day, and the two patterns that matter most.

The sender algorithm toolkit

  • just(vals...)Sender factory. Completes immediately with given values. Starting point when not using a scheduler.
  • schedule(sched)Sender factory. Schedules a kick-off on an execution context. Chain work with then().
  • then(sndr, fn)Transform success values synchronously. The result of fn becomes the new value downstream.
  • let_value(sndr, fn)Like then but fn returns a sender — for chaining operations that are themselves async.
  • sync_wait(sndr)Consumer. Blocks calling thread until sender completes. Returns optional<tuple<values...>>. In the final standard it lives in std::this_thread::sync_wait; stdexec spells it stdexec::sync_wait.

The two patterns that matter

Fan-out with when_all

// Three operations run concurrently
auto work = stdexec::when_all(
    stdexec::starts_on(sched,
        async_read(fd_a) | stdexec::then(process)),
    stdexec::starts_on(sched,
        async_read(fd_b) | stdexec::then(process)),
    stdexec::starts_on(sched,
        async_read(fd_c) | stdexec::then(process))
)
| stdexec::then([](A a, B b, C c) {
    return combine(a, b, c); // after all three
});

No blocking between steps. No thread-per-operation. One clean join point.

Scheduler hand-off with continues_on

// Three schedulers, one pipeline.
async_recv(io_sched, socket, buf)      // on your ring

| stdexec::continues_on(gpu_sched)     // hand off
| stdexec::then([](Buffer b) {
      return process_data(b);       // runs on GPU
  })

| stdexec::continues_on(io_sched)      // back to ring
| stdexec::let_value([](Result r) {     // fn returns a SENDER
      return async_write(io_sched, file, r);
  });

Swap CPU↔GPU and the control flow doesn't change. Errors and cancellation cross scheduler boundaries automatically.

Say the then/let_value distinction, don't slide it: then's callable returns a value, let_value's returns a sender — that's the whole rule, and the async_write step on the right is the live example. Full side-by-side comparison is Appendix A if anyone wants it. Renames: continues_on was transfer, on became starts_on, and a new round-trip on was added (P3175, folded into P2300R10); stdexec keeps the old spellings as aliases. Why starts_on on the left but not the right: async_recv(io_sched, …) takes its scheduler, so the sender is context-bound by construction and places itself; async_read(fd) is context-free, so it gets placed with starts_on. Two idioms: context-carrying senders place themselves, context-free work gets placed. Caveat: self-placing means the factory must tolerate start() from any thread — marshal to the ring, exactly like fiberexec's cancel queue. If probed on the last step: let_value means the pipeline's completion IS the write's completion — sync_wait genuinely waits for the write to finish. If probed on the (A a, B b, C c) signature: each when_all branch returns exactly one value; a branch returning void or multiple values changes the downstream signature — check completion signatures when you hit surprising compile errors. Say, don't show: this is essentially impossible to do cleanly with std::future, hand-rolled callbacks, or most coroutine frameworks. Once sender-based async_recv / async_write exist this compiles as written; today you'd wrap your own io_uring layer to produce them. GPU caveat: you'd still manage host-device transfer; nvexec has facilities.

async_scope — fire-and-forget, still structured

// stdexec today
exec::async_scope scope;

scope.spawn(
    stdexec::starts_on(sched, do_work())
);
// caller continues immediately...

stdexec::sync_wait(scope.on_empty());
// ...but all spawned work is done here ✓
// C++26 — not just a rename
namespace ex = std::execution;
ex::counting_scope scope;

ex::spawn(ex::starts_on(sched, do_work()),
          scope.get_token());     // ← token

std::this_thread::sync_wait(scope.join());

The old model gives two bad choices: block on everything, or detach and hope. This is the third option — spawn work and continue, while the scope tracks every outstanding operation and you choose exactly when to join.

spawn takes a scope token, not the scope — that indirection is what lets a scope live safely as a data member. counting_scope also gives you close() and request_stop(); simple_counting_scope is the same type without stop support (P3149).

spawn requires a sender that completes with no values — hence do_work() returning void. Need the result? That's spawn_future. And spawn is one of the few places the model allocates — by design.

If jthread comes up: std::jthread fixes the lifetime problem — genuinely useful — but it's still a thread: can't run on a scheduler, can't compose with when_all, can't propagate errors out. A jthread is a hammer; a sender scope is a grammar. Both scope types, if asked: counting_scope = simple_counting_scope + request_stop. Same state machine, same token machinery, and — the part that matters two slides from now — identical destructors: terminate unless the scope is joined, unused, or unused-and-closed. If asked how faithful stdexec is here: exec::async_scope predates P3149 and the shapes differ — on_empty() vs join(), scope-as-argument vs token. Porting is mechanical but it is not sed. The point to land: spawn is where structured concurrency meets reality — you genuinely need unbounded fan-out sometimes, and this is the version that still lets you prove everything finished.

The Ecosystem
Where things
actually stand

What exists, what it does, and the honest picture on standard library support and async I/O.

The road to P2300

  • 2005–07Async I/O starts it all — Asio appears (2005); Kohlhoff's networking proposals enter the committee (N2175, 2007). The Networking TS grows from here — and its need for an executor model triggers everything below.
  • 2011C++11 — std::thread, std::future, std::async. Useful primitives. No composable model. The complaints start immediately.
  • 2012–21The executor wars — years of competing proposals; P0443 unified executors runs until senders replace it. The Networking TS stalls waiting for an executor model that never lands.
  • 2018–19Libunifex developed at Facebook, open-sourced 2019. Eric Niebler and colleagues build a production sender/receiver system — the field-experience foundation for P2300.
  • 2019–20io_uring lands in kernel 5.1. C++20 coroutines land as language features with no standard library support.
  • 2021–23P2300 R0 — Niebler, Lelbach, Baker et al. submit the sender/receiver proposal; NVIDIA funds stdexec as the reference implementation. Over the next two years direction settles on senders, the Networking TS is not pursued, and sender-based networking restarts as P2762 (2023).
  • Jun 2024P2300R10 adopted at WG21 St. Louis plenary — but narrowly: roughly a third of the room voted against, on grounds of complexity and teachability.
  • Mar 2026C++26 technical work completed March 28 in London (Croydon). DIS ballot / ISO publication pending. Compiler stdlib implementations: no public progress visible as of August 2026.

All along, underneath: every shop builds its own async framework from whatever primitives exist — or on Boost. That has been continuous since before C++11, it is still going on, and it is precisely why none of our systems compose.

The band under the timeline is the one to make personal: every place you have worked since 2006 has built or maintained an in-house async framework. The rows above are what the committee was doing; the band is what the rest of the industry was doing the whole time, and it never stopped waiting for them. Say it in first person — it's the line that earns the room's agreement before you ask them for anything. The punchline of this slide, say it: the standardization effort that STARTED with async I/O ended, twenty years later, with a standard async model containing everything EXCEPT the I/O. The Networking TS died so senders could live, and the senders shipped without the sockets. If asked who objected in St. Louis, and why: the minutes record individual objections, not national-body ones — Sutter polled the other NBs and found none. The substance: sender/receiver complexity is extremely high; an average programmer can't and won't use it; "what we are developing is a full language in the library"; and the teaching story for beginners is missing. Worth drawing the thread forward out loud: those 2024 objections were complexity and documentation, and Sutter's 2026 warning is documentation and missing helper libraries — same complaint, two years apart, from opposite sides of the vote. For the P0443 veterans in the room: P2300 didn't descend from the TS — its design lineage is Facebook's pushmi/libunifex. The connection is the executor layer: the TS's needs fed unified executors (P0443, Kohlhoff co-authored), P2300 replaced P0443, and the P2444-vs-P2464 debate settled it in senders' favor.

C++26 is finalized. No shipping standard library exposes std::execution. Each claim below names the artifact it comes from — check them yourself, they move.

GCC / libstdc++

The <execution> header exists but only wires up C++17 parallel policies via Intel TBB. No P2300 code in the source tree; no public timeline. (GCC 16 shipped reflection and contracts first.)
source: libstdc++ tree + C++26 status page

Clang / libc++

The C++26 status page lists P2300R10 with a blank status and no version number — work hasn't started, or isn't tracked. No public timeline.
source: libc++ Cxx26 status page

MSVC / Microsoft STL

A tracking issue exists (microsoft/STL #4768) listing P2300R10 and its follow-ons with planned feature-test macros. The issue carries a note — dated 2024 — that C++26 PRs won't be accepted until C++23 library work is finished.

None of that has shipped in any stdlib either — but "the standard has no scheduler or task type" is no longer true on paper.

NVIDIA stdexec github.com/NVIDIA/stdexec

The reference implementation, now well beyond P2300 core. Header-only; requires C++20 or later.

In stdexec/ — P2300 core:

  • All core concepts, CPOs, and algorithms
  • run_loop scheduler (single-thread event loop)
  • Coroutine as_awaitable integration

In exec/ — extensions beyond P2300:

The Beman Project github.com/bemanproject/execution

Volunteer-run, founded C++Now 2024. Goal: clean, spec-faithful implementations suitable for eventual upstreaming into libstdc++ / libc++.

What it implements:

The Gap
The I/O problem
nobody talks about

The model is ready. The composition story is ready. The async I/O primitives most C++ engineers actually need day-to-day are not.

P2300 deliberately excludes I/O — here's what that means

Intentional, not an oversight. P2300 was scoped to the execution framework only; concrete I/O is a separate layer on top, and the authors have always said networking and file I/O are C++29 territory.

What stdexec's io_uring integration actually is:

  • A genuine scheduler — schedule, timers (async_wait), stop propagation
  • Not a toy: the wiring compiles, runs, and cancels correctly
  • But the repo example only demonstrates cancellation flow
  • No I/O operations: no async_read, async_write, async_accept, async_connect

GitHub issue #1062: "io_uring reading files." Filed 2023. The only response was a link to a separate external project. That's the current state.

What actually exists for sender-based I/O:

  • Asio + Leahy's stdexec adaptation — the only viable production path today. Real async file I/O (stream_file, random_access_file) and network I/O exposed as senders (CppCon 2025). Needs Asio; io_uring on Linux (BOOST_ASIO_HAS_IO_URING), IOCP on Windows.
  • uring_exec — thin wrapper over every io_uring_prep_* op. Has read, write, accept, send, recv. Linux only. Research-grade.
  • maikel/senders-io — more designed file + network senders. Stale, old stdexec API.
  • Beman net (P2762) — the sender-based standards-track approach. Very early. C++29 target.
  • P4003 / P4007 (C++ Alliance) — a competing coroutine-first direction. P4003 "Ask: A Minimal Coroutine Execution Model" (Falco, Gill, Gerbino; R3 May 2026) goes to LEWG at Brno, alongside P4007 "Senders and Coroutines" and the Network Endeavor paper series.
  • Intel bare-metal senders — P2300 subset for embedded/interrupt-driven I/O. No OS required.

Already on Asio with io_uring? Leahy's adaptation is the most complete sender-based I/O available today. Everyone else is in DIY territory.

The question you will get, so ask it first: "isn't the C++ Alliance pushing a different answer?" Yes — as of the Croydon meeting there are two live standards-track directions for async I/O, sender-based (P2762) and coroutine-first (P4003/P4007), and the committee has not chosen. That uncertainty is an argument FOR the talk's thesis, not against it: whichever wins, the safe move today is your own I/O behind a sender-shaped seam you control. Don't editorialize about which is better — you don't have a dog in that fight and half the room might. History, worth a beat: libunifex — the Facebook library P2300 grew out of — had working io_uring and epoll schedulers. That I/O coverage was deliberately left out of standardization scope. The gap didn't happen by accident; it was a scoping decision.

  • Community projects exist (uring_exec, maikel/senders-io, and my own fiberexec) — research-grade, not production
  • File I/O and network sockets both technically possible

For raw socket users on any platform today: wrap your existing async layer to produce senders. The computation model is ready. The I/O layer is yours to bring.

The bridge: wrapping your existing async I/O as senders

If you have an io_uring scheduler, epoll loop, or any callback-based system — expose it as a scheduler today and gain composability without rewriting anything.

// Your existing C-style async API:
// void async_read(int fd, char* buf, size_t len,
//   void(*cb)(int result, void* ctx), void* ctx);

// Wrap it as a sender:
struct read_sender {
    using sender_concept = stdexec::sender_t;
    using completion_signatures = stdexec::completion_signatures<
        stdexec::set_value_t(std::size_t),
        stdexec::set_error_t(std::error_code),
        stdexec::set_stopped_t()>;  // you cancel — declare it

    int fd; char* buf; std::size_t len;

    auto connect(stdexec::receiver auto rcvr) && {
        return read_op<decltype(rcvr)>{fd, buf, len, std::move(rcvr)};
    }
};

// Now your I/O flows into any sender pipeline:
auto work = read_sender{fd, buf, 4096}
          | stdexec::then(parse) | stdexec::then(process);

This is the practical adoption path right now for I/O engineers: keep your existing async I/O layer, expose it as a sender, gain composability at the computation level today. This part is boilerplate — the next slide is where the heavy lifting happens.

Niebler's blog "What are Senders Good For, Anyway?" (Feb 2024) walks this pattern in detail — wrapping a C-style async API to produce senders. Essential reading.

When standard I/O senders eventually arrive (P2762, C++29+), you swap the wrapper for the standard primitive. The pipeline logic above doesn't change.

The operation state — where the real work lives

// using namespace stdexec; — elided below for width
template <stdexec::receiver R>
struct read_op {
    using operation_state_concept = operation_state_t;
    read_op(read_op&&) = delete;      // pinned: built in place

    void start() & noexcept {
        // 1. hook the receiver's stop token into YOUR layer
        stop_.emplace(get_stop_token(get_env(rcvr_)), on_stop{this});
        // 2. submit; `this` is the completion context
        ::async_read(fd_, buf_, len_, &on_complete, this);
    }

    static void on_complete(int result, void* ctx) noexcept {
        auto& self = *static_cast<read_op*>(ctx);
        self.stop_.reset();          // unregister BEFORE completing

        if (result >= 0)
            set_value(std::move(self.rcvr_), std::size_t(result));
        else if (result == -ECANCELED)
            set_stopped(std::move(self.rcvr_));     // not an error!
        else
            set_error(std::move(self.rcvr_),
                      std::error_code(-result, std::system_category()));
    }

    int fd_; char* buf_; std::size_t len_; R rcvr_;
    std::optional</* R's stop-callback type */> stop_;
};

Pinned, caller-owned storage. connect() constructs the op state in place and it never moves. This is where "no allocation on the default path" actually comes from — it isn't a slogan, it's this = delete.

Stop callback lifetime. Registered in start(), torn down before the completion fires. Get that ordering wrong and you have a use-after-free on the cancellation path — the bug that doesn't show up until production.

Three-way completion is the whole game. -ECANCELED maps to set_stopped, not set_error. Collapse those two and every upon_stopped downstream is dead code.

Slow down here. The pipeline syntax is familiar to this room; the seam is the part that's worth their time. Walk it in three beats: pinned storage (that's the zero-overhead claim, made concrete), stop-callback ordering (the use-after-free), three-way completion (the difference between real and decorative cancellation). If asked "where's the constructor?": the deleted move ctor makes read_op a non-aggregate, so brace-init on the previous slide needs a real constructor — elided here for space. Say "the ctor is the obvious one" and move on; don't pretend the slide compiles as printed. If asked about the stop_ declaration: yes, it's ugly — you need the receiver's own stop-token type, not std::stop_callback, because in-place stop sources are the common case. Real code hides it behind an alias. If asked why connect is &&-qualified: these are single-shot senders; connecting from an lvalue is how you accidentally submit the same op twice. Bridge to the next slide: "that -ECANCELED branch is one arrow in a longer round trip — here's the whole thing."

Before you wrap: two things to watch out for

Watch out: older stdexec examples and early P2300 talks use tag_invoke for customization — friend auto tag_invoke(connect_t, ...) etc. That mechanism was replaced in P2300R10, the final adopted revision. The C++26 standard uses plain member functions: connect(), start(), set_value(), and using sender_concept = sender_t. The code on the previous two slides reflects the correct final style.

Cancellation: wire the receiver's stop token into your layer's own cancellation so set_stopped() is real, not decorative — it's where hand-rolled wrappers are most likely to cut corners. Here is the flow from fiberexec, a personal research runtime where I did this integration end to end — fibers inside, senders outside:

The unwind is fiber-internal — it's how a suspended fiber abandons its stack without checking a return code at every await point. It never crosses the seam; the sender world only ever sees set_stopped().

If challenged on the completion_signatures typedef: the nested using completion_signatures = ... is what stdexec accepts and what almost every example shows; the standard also specifies a member get_completion_signatures(env) form. Re-check which spelling the final wording blesses before the talk, and if unsure, say "that's the stdexec spelling" rather than "that's the standard spelling." Introduce fiberexec in one sentence, then move on: personal research runtime, research-grade and not production, held to exactly the standard this deck applies to everyone else's project. Repo is on the references slide. Narrate the U-shape: the stop request crosses the seam twice — down into the kernel as ASYNC_CANCEL, back up as set_stopped. That round trip is what "cancellation is real" means. This is fiberexec's verified flow (run.hpp + fiber_context.cpp), not pseudocode. Pre-empt the cost question, don't wait for it: yes, there's a throw inside the fiber — one unwind per cancelled operation, off the hot path. The alternative is threading an error check through every suspension point in the fiber, which is the exact thing fibers exist to avoid. Say this before someone asks; it reads as ownership rather than scramble. Why ③ says "queued": the stop_callback runs on whatever thread called request_stop — not the ring's owner — and only the owning thread may touch the SQ ring. So request_cancel does a mutex-guarded queue push plus an eventfd write to wake the ring; the owning thread drains the queue into ASYNC_CANCEL SQEs on its next pass (ring-full handled: leftovers wait for the next wakeup). Bonus detail if probed: linked SQE chains cascade -ECANCELED; already-completed ops return -ENOENT and are discarded.

Adoption is workload-dependent

Compute-heavy async work

(parallel pipelines, GPU offload, CPU-bound task graphs)

  • stdexec's story is good here today
  • Thread pool + GPU schedulers are the most mature part
  • when_all, bulk, nvexec all work well in practice
  • Consider adopting stdexec now if you can tolerate API churn

HPC, scientific computing, GPU pipelines — this is the most compelling case for adoption today. The model was built for this use case first.

I/O-heavy async work

(network servers, file pipelines, embedded I/O, storage systems)

  • The composition model is sound and ready
  • The I/O primitives are not production-ready
  • Pragmatic path: wrap your existing async layer as senders
  • Use stdexec's async_scope for structured spawn patterns
  • Gain composability now; swap I/O layer when P2762 ships

As Leahy demonstrated at CppCon 2025 — don't rewrite, adapt. Your existing io_uring / epoll / socket code stays; the computation layer above it gains P2300 composability now.

Universal: Learn and experiment with stdexec on Godbolt now. Plan production adoption when libstdc++ or libc++ ships P2300 (likely 2–4 years). The concepts won't change even if the headers do.

Summary

  • ▸Why: every pre-P2300 async codebase is correct but isolated — the standard gave us primitives, never a model.
  • ▸What: senders are lazy, composable descriptions of work; the scheduler is swappable — your io_uring ring can be one.
  • ▸The gap: C++26 is done, but no stdlib ships it (likely 2–4 years) — and P2300 deliberately excludes I/O.
  • ▸The bridge: wrap your existing async I/O layer as senders today; swap in standard I/O when P2762 lands.
  • ▸Not just sugar: a callback is a function you give away; a sender is a value you keep — which is why the consumer, not the algorithm, decides how work runs.
  • ▸Not just destructors: the language forbids async construction and destruction outright, so cleanup that does I/O has to live somewhere else — and async RAII is being built in the sender domain.
  • ▸Verdict: learn now, plan carefully. Compute-heavy: adopt. I/O-heavy: adapt, don't rewrite.
Dropped nuance, deploy if useful: structured concurrency makes the safe path the default — child work completes before the parent scope exits. Standard names are continues_on / starts_on (stdexec keeps transfer / on as aliases). stdexec is experimental with ongoing API churn (a Dec 2025 PR dropped its non-conforming static connect members); Beman tracks spec fidelity for eventual stdlib upstreaming.

Appendix A · reference for Q&A — not presented live

then vs let_value

The whole rule: then's callable returns a value; let_value's returns a sender. Reach for let_value whenever the next step is itself asynchronous.

then — synchronous transform

just(x) | then([](int x) {
    return x * 2;      // a value ✓
});
// downstream sees: set_value(int)

Runs on whatever context the previous step completed on. No new async work is introduced.

let_value — chain in async work

just(path) | let_value([&](string p) {
    return async_read(sched, p);
    // ↑ a sender ✓
})
| then([](Buffer buf) {
    return parse(buf);
});

The returned sender is connected and started; the pipeline's completion is its completion. This is how you nest one async operation inside another.

The common mistake: using then with a callable that returns a sender. It compiles — and gives you a value completion carrying an unstarted sender that nobody ever connects. The work silently never runs.

Pull this up if someone asks for the distinction in code. The failure mode in the red box is the one worth saying out loud — it's the quiet bug, not a compile error, and everyone hits it once. If pushed further: let_value keeps the predecessor's values alive for the duration of the returned sender, which is why the lambda can capture and reference them; then's result is moved downstream immediately.
Appendix B · reference for Q&A — not presented live

Structured concurrency — safety by construction

The old way — danger

// Thread may outlive `data`
std::thread([&data] {
    process(data); // dangling ref! 💥
}).detach();
// data destroyed here

Detached threads are a well-known footgun. No way to know when — or whether — they complete.

The sender way — safe

// Work is nested — cannot outlive scope
stdexec::sync_wait(
    stdexec::starts_on(sched,
        stdexec::just(data)
        | stdexec::then(process)
    )
);
// Guaranteed: process() is done here ✓

Child work completes before the parent scope exits — and P2300 removed the escape hatches (start_detached, ensure_started) before shipping, so the unstructured version is no longer a one-liner.

Do NOT show this unprompted: the detached-thread panel is a strawman for this room. It exists only in case someone asks how senders compare to raw threads. Don't overclaim this one: a counting_scope you never join is still a bug, and you can still write unstructured code by hand. What changed isn't a guarantee, it's that the committee took the easy detach out of the standard before it shipped — that's a fact about their behaviour, which is a stronger thing to say than a promise about yours. If jthread comes up: std::jthread fixes the lifetime problem — genuinely useful — but it's still fundamentally a thread: can't run on a scheduler, can't compose with when_all, can't propagate errors out. A jthread is a hammer; a sender scope is a grammar. And yes, you can still misuse the low-level primitives — the high-level API steers you away from it.
