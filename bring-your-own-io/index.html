01
The Problem
Why async C++
has been broken

The standard library gave us primitives. It never gave us a model. So we all built our own — and none of them compose.

The problem, concretely

Four years ago I built an async I/O scheduler with a common interface backed by two implementations: io_uring in production, and a thread pool fallback for environments where io_uring isn't available. It has cancellation via stop tokens.

This was standard practice — every shop with serious async needs built some version of it. And every one of those systems, mine included, hits the same structural ceiling:

  • ✗No two of them compose. Work pipelines are ad-hoc plumbing; integrating another team's async domain means writing a custom bridge — every time.
  • ✗None of them share a vocabulary. My interface is mine, Asio's is Asio's — no generic algorithm can span them.
  • ✗Each one invents error and cancellation propagation. Exceptions here, error_codes there, silent drops somewhere else.

These aren't design mistakes — they're the ceiling any single-team library hits, because composing across teams needs a vocabulary everyone shares, and only a standard can provide one. P2300 takes the instinct we all had — separate computation from execution context — and makes it universal.

The prior art — what every large C++ shop built:

  • Team A uses Boost.Asio with callbacks
  • Team B uses hand-rolled thread pool + futures
  • Team C wrote a coroutine framework
  • You wrote an io_uring scheduler
  • None of these compose with each other
  • Each has its own error propagation story
  • Each has its own cancellation story — or doesn't

P2300's pitch: a vocabulary layer that all of these can speak. Work from any source composable with any other source, using generic algorithms.

Delivery: the ✗s are coordination failures, not engineering failures — no amount of skill fixes them from inside one team, because they require everyone else to agree on a vocabulary. Land that sentence before advancing; it's the whole reason the fix is a standard and not a better in-house library. Your system stays on stage as the exemplar of standard practice, not the patient.

Why std::future isn't the model — and what is

What's broken

  • ✗No continuations. .then() has been stuck in the Concurrency TS since 2013 — chaining means blocking on .get() or spawning another thread.
  • ✗No cancellation, no readiness callback. You poll in a loop or you block.
  • ✗No scheduler control. std::async runs work wherever it likes — implementation-defined.
  • ✗Blocking fan-in, messy errors. Join N futures serially; exceptions hide in shared state, incompatible with error_code I/O.

What a real model needs

  • ✓Composable continuations. Chain, fan-out, fan-in — one syntax regardless of what's underneath.
  • ✓First-class cancellation. Stopped is its own completion channel, not an exception in disguise.
  • ✓Scheduler-agnostic. Thread pool, GPU, io_uring ring, interrupt handler — the computation shouldn't care.
  • ✓Uniform completion. Value / error / stopped, propagated automatically through the chain.

Each ✗ maps to the ✓ beside it. Two more requirements we'll meet in the model section: zero overhead on the default path (allocation opts in, never sneaks in) and structured lifetimes — child work completes before its parent scope exits.

Detail dropped from the slide: futures always heap-allocate shared state, even for trivial work. launch::deferred is laziness without value — runs on the retrieving thread, can't target a scheduler, can't compose. jthread fixes thread lifetime but is still a thread: no when_all, no error propagation out. The coroutine ecosystem's failure modes are different — next slide.

What about coroutines?

C++20 gave us the coroutine mechanism — co_await and co_return — but almost no library to use it with. The problems below aren't with coroutines themselves; they're with the missing infrastructure around them.

  • ✗No standard scheduler. Every coroutine library — cppcoro, Asio, folly, libunifex — independently reinvented where coroutines run and how they're scheduled.
  • ✗No structured cancellation. Cancelling a coroutine chain requires library support — there's nothing in the language to propagate stop signals.
  • ✗Fan-out is awkward. co_await is sequential by nature. Concurrent fan-out requires library primitives that don't exist in the standard.
  • ✗No scheduler portability. A coroutine written against Asio's executor doesn't compose with one written against a custom io_uring scheduler.

The good news: they interoperate

P2300 deliberately treats coroutines as a first-class citizen. You don't have to choose.

// co_await any sender inside a coroutine
exec::task<int> my_coroutine() {
    // sender becomes awaitable
    auto val = co_await stdexec::just(42)
                   | stdexec::then([](int x) {
                         return x * 2;
                     });
    co_return val;
}

// A coroutine task is itself a sender
auto work = stdexec::when_all(
    my_coroutine(),   // sender ✓
    other_work()      // sender ✓
);

Use co_await for sequential async steps where it reads well. Use sender algorithms for parallelism, fan-out, and scheduler control. Compose them freely.

Framing line before advancing: coroutines and std::future have DIFFERENT failure modes — futures fail at composability; the coroutine ecosystem fails at parallelism, cancellation, and portability. P2300 provides the missing infrastructure and treats coroutines as a first-class citizen in the process.
02
The Model
Three abstractions.
One vocabulary.

Scheduler · Sender · Receiver — and why as a user you mostly only deal with one of them.

The core vocabulary

📍

Scheduler

A lightweight handle to an execution context — thread pool, GPU stream, io_uring ring, interrupt handler. Answers: "where does work run?"

This is what you provide when you plug in your own I/O layer. Your io_uring ring becomes a scheduler.

📦

Sender

A description of async work — lazy, composable, zero-overhead until started. Like a recipe, not a running computation.

This is what you spend 95% of your time with as a user.

📬

Receiver

A generalized callback with three channels: value, error, and stopped. Glue between senders inside the framework.

As a user you almost never write these. Algorithms handle them internally.

The key insight: senders are values. Pass them around, compose them, store them. No work happens until you explicitly start them with a consumer like sync_wait().

Senders are lazy — work is a value

// Nothing runs yet. This is just a description.
auto work =
    stdexec::schedule(sched)           // start on scheduler
    | stdexec::then([] {
          return compute_something();   // runs on scheduler
      })
    | stdexec::then([](auto result) {
          return transform(result);      // also on scheduler
      });

// Work STARTS here. Calling thread blocks until done.
auto [value] = stdexec::sync_wait(work).value();
// Swap the scheduler — pipeline logic is unchanged.
auto cpu_work  = pipeline(thread_pool_sched);
auto gpu_work  = pipeline(cuda_stream_sched);
auto ring_work = pipeline(io_uring_sched);  // your scheduler!

Pipeline built left-to-right with |. Each step returns a new sender — nothing executes.

sync_wait() is the consumer — it connects everything and starts execution.

The full pipeline can be stored, passed to functions, or modified before running. This is what composability actually means.

Say, don't show: if your scheduler is an io_uring ring, pipeline(ring_sched) routes all that work through your ring — the computation logic is unchanged. This is the hook back to the audience's own infrastructure.

Three ways work completes — all uniform

set_value(args...)
Success. Zero or more result values forwarded downstream. A sender can complete with multiple independent values in a single call — something std::future cannot express at all.

set_error(err)
Failure. exception_ptr, error_code, or any type. Propagates automatically through the chain.

set_stopped()
Cancellation. Structured and explicit — not an exception, not an error code.

// Errors propagate automatically — no try/catch at every step
auto pipeline =
    async_read(sched, fd, buf)         // might set_error()
    | stdexec::then([](Buffer b) {
          return parse(b);               // only runs if no error
      })
    | stdexec::upon_error([](std::error_code ec) {
          log_error(ec);
          return fallback_value();        // recover and continue
      })
    | stdexec::upon_stopped([] { cleanup(); });

One uniform completion story — no more per-library mix of exceptions, error codes, and silent failures.

Say, don't show: the multi-value capability is why sync_wait always returns optional<tuple<...>> even for one value — the optional is empty on cancellation, the tuple carries all values. when_all uses this to deliver one result per branch in a single completion.
03
The API
Writing sender code
in practice

The algorithms you'll use every day, and the two patterns that matter most.

The sender algorithm toolkit

  • just(vals...)Sender factory. Completes immediately with given values. Starting point when not using a scheduler.
  • schedule(sched)Sender factory. Schedules a kick-off on an execution context. Chain work with then().
  • then(sndr, fn)Transform success values synchronously. The result of fn becomes the new value downstream.
  • let_value(sndr, fn)Like then but fn returns a sender — for chaining operations that are themselves async.
  • when_all(sndrs...)Fan-in. Runs all senders concurrently, completes when all finish. Returns tuple of all results.
  • upon_error(sndr, fn)Handle errors mid-chain. Recover and continue, rethrow, or return a fallback value.
  • sync_wait(sndr)Consumer. Blocks calling thread until sender completes. Returns optional<tuple<values...>>. In the final standard it lives in std::this_thread::sync_wait; stdexec spells it stdexec::sync_wait.
Mention verbally, not row-by-row: upon_stopped(sndr, fn) — handle cancellation explicitly mid-pipeline (already shown in code on the three-channels slide). bulk — parallel for over indices 0..n-1; final C++26 bulk takes an execution policy (P3481) and adds bulk_chunked / bulk_unchunked; older stdexec examples show bulk(sndr, n, fn). Speak to five only: just, schedule, then, let_value, sync_wait — the demo uses exactly these. The rest are "on the slide for your reference."

The two most important patterns

Fan-out with when_all

// Three operations run concurrently
auto work = stdexec::when_all(
    stdexec::starts_on(sched,
        async_read(fd_a) | stdexec::then(process)),
    stdexec::starts_on(sched,
        async_read(fd_b) | stdexec::then(process)),
    stdexec::starts_on(sched,
        async_read(fd_c) | stdexec::then(process))
)
| stdexec::then([](A a, B b, C c) {
    return combine(a, b, c); // after all three
});

No blocking between steps. No thread-per-operation. One clean join point.

Chaining async with let_value

// then() — fn returns a plain value
just(x) | then([](int x) {
    return x * 2;   // value ✓
});

// let_value — fn returns a sender
just(path) | let_value([&](string p) {
    return async_read(sched, p);
    // ↑ sender ✓ — async op chained in
})
| then([](Buffer buf) {
    return parse(buf);
});

Use then for sync transforms. Use let_value when the next step is itself async.

Why starts_on, not on: since P3175, on(sch, s) is the round-trip adaptor — it hops completion back to the environment's current scheduler, and is ill-formed when the env has none (e.g. inside scope.spawn). starts_on says exactly what these examples mean: start the work there, no return hop. stdexec implements the new semantics too. Caveat if asked about the (A a, B b, C c) signature: each when_all branch here returns exactly one value. A branch returning void or multiple values changes the downstream signature — check the completion signatures when you hit surprising compile errors.

Composing schedulers — the real payoff

continues_on(sndr, sched) hands execution off to a different scheduler mid-pipeline. (Renamed from transfer in P2300R10; the old on is now starts_on, with a new round-trip on added. stdexec keeps the old spellings as aliases.) This is something no hand-rolled async system does cleanly.

// Three schedulers, one pipeline.
// Each step runs where it makes sense.

auto pipeline =
    // 1. Receive data on the io_uring ring
    async_recv(io_sched, socket, buf)

    // 2. Hand off to GPU/CPU for compute
    | stdexec::continues_on(gpu_sched)
    | stdexec::then([](Buffer b) {
          return process_data(b);   // continuation runs on GPU context
      })

    // 3. Continue on io_uring to write result
    | stdexec::continues_on(io_sched)
    | stdexec::let_value([](Result r) {
          return async_write(io_sched, file, r);  // returns a sender — chained in
      });

stdexec::sync_wait(std::move(pipeline));

Why this matters

  • Each scheduler is independently sourced — io_uring from your own layer, thread pool or GPU from stdexec or nvexec
  • Swap the compute scheduler CPU↔GPU — the control flow doesn't change
  • Error and cancellation propagate across scheduler boundaries automatically — no special handling at the transfer points

This is the pipeline pattern that motivated P2300 in the first place — heterogeneous execution where the computation describes what runs where, not the scheduler.

Say, don't show: this is essentially impossible to do cleanly with std::future, hand-rolled callbacks, or most coroutine frameworks. And: once sender-based async_recv / async_write exist, this pipeline compiles as written — today you'd wrap your own io_uring layer to produce those senders. GPU caveat: you'd still manage host-device memory transfer; nvexec has facilities. If probed on step 3: let_value means the pipeline's completion IS the write's completion — sync_wait genuinely waits for the write to finish. "Isn't continues_on(io_sched) redundant if async_write is already bound to the ring?" — it repositions where the lambda itself runs; kept here to show scheduler hand-off, which is the point of the slide.

Structured concurrency — safety by construction

The old way — danger

// Thread may outlive `data`
std::thread([&data] {
    process(data); // dangling ref! 💥
}).detach();
// data destroyed here

Detached threads are a well-known footgun. No way to know when — or whether — they complete.

The sender way — safe

// Work is nested — cannot outlive scope
stdexec::sync_wait(
    stdexec::starts_on(sched,
        stdexec::just(data)
        | stdexec::then(process)
    )
);
// Guaranteed: process() is done here ✓

Child work always completes before the parent scope exits — the default of the model, not a discipline you maintain.

If jthread comes up: std::jthread fixes the lifetime problem — genuinely useful — but it's still fundamentally a thread: can't run on a scheduler, can't compose with when_all, can't propagate errors out. A jthread is a hammer; a sender scope is a grammar. And yes, you can still misuse the low-level primitives — the high-level API steers you away from it.

async_scope — fire-and-forget, still structured

exec::async_scope scope;

scope.spawn(
    stdexec::starts_on(sched, do_work())
);
// caller continues immediately...

stdexec::sync_wait(scope.on_empty());
// ...but all spawned work is done here ✓

The old model gives two bad choices: block on everything, or detach and hope. This is the third option — spawn work and continue, while the scope tracks every outstanding operation and you choose exactly when to join.

Standardized in C++26 as counting_scope / spawn / spawn_future (P3149). Note: spawn is one of the few places the model allocates — by design.

The Ecosystem
Where things
actually stand

What exists, what it does, and the honest picture on standard library support and async I/O.

The road to P2300

  • 2005Async I/O starts it all — Kohlhoff's Boost.Asio-based networking proposals bring asynchronous I/O into the standards process. The Networking TS grows from here — and its need for an executor model triggers everything below.
  • 2011C++11 — std::thread, std::future, std::async. Useful primitives. No composable model. The complaints start immediately.
  • 2012–18The executor wars — years of competing proposals, multiple rounds through the committee. The Networking TS stalls waiting for an executor model that never lands. No consensus on the async model.
  • 2018Libunifex born at Facebook. Eric Niebler and colleagues build a production sender/receiver system. This becomes the field-experience foundation for P2300.
  • 2019–20Many of us write our own async systems out of necessity. io_uring lands in kernel 5.1. C++20 coroutines land as language features with no standard library support.
  • 2021P2300 R0 — Niebler, Lelbach, Baker et al. submit the sender/receiver proposal. NVIDIA funds stdexec as the reference implementation. Senders win; the Networking TS path is retired, to restart as sender-based P2762.
  • Jun 2024P2300R10 adopted at WG21 St. Louis plenary — consensus, but with notable minority opposition reflecting concerns about complexity and review thoroughness.
  • Mar 2026C++26 technical work completed March 28 in London (Croydon). DIS ballot / ISO publication pending. Compiler stdlib implementations: no public progress visible as of August 2026.
The punchline of this slide, say it: the standardization effort that STARTED with async I/O ended, twenty years later, with a standard async model containing everything EXCEPT the I/O. The Networking TS died so senders could live, and the senders shipped without the sockets. For the P0443 veterans in the room: P2300 didn't descend from the TS — its design lineage is Facebook's pushmi/libunifex. The connection is the executor layer: the TS's needs fed unified executors (P0443, Kohlhoff co-authored), P2300 replaced P0443, and the P2444-vs-P2464 debate settled it in senders' favor.

The standard library situation

C++26 is finalized. The standard library implementations are not.

GCC / libstdc++

The <execution> header exists but only wires up C++17 parallel policies via Intel TBB. The source tree has no P2300 code — no visible implementation work or public timeline. (GCC 16 prioritized reflection and contracts.)

Clang / libc++

The official C++26 status page lists P2300R10 with a blank status and no version number. Work hasn't started or isn't tracked. No public timeline.

MSVC / Microsoft STL

A tracking issue exists (microsoft/STL #4768) with planned feature test macros documented. However the team has explicitly stated no C++26 PRs will be accepted until remaining C++23 work is complete. Nothing shipped.

#include <execution> today gets you C++17 parallel policies only — not P2300. The sender/receiver framework is not in any shipping standard library across GCC, Clang, or MSVC. Likely arrival: 2–4 years based on precedent, but no public timelines from any vendor.

And C++26 execution is bigger than P2300: the standard also adopted counting_scope / spawn (P3149), a standard parallel_scheduler system context (P2079), a coroutine task type std::execution::task (P3552), and a policy-taking bulk (P3481). None of that has shipped in any stdlib either — but "the standard has no scheduler or task type" is no longer true on paper.

Precedent, if asked "why so slow?": std::format took ~3 years to land in both libstdc++ and libc++ after C++20 — and P2300 is far larger. The standardization-to-implementation gap is normal, not a red flag; it just matters for adoption planning.

The Beman Project github.com/bemanproject/execution

Volunteer-run, founded C++Now 2024. Goal: clean, spec-faithful implementations suitable for eventual upstreaming into libstdc++ / libc++.

What it implements:

  • Essentially the entire C++26 execution surface — vocabulary and all algorithms, tracked clause-by-clause
  • just, then, let_value, starts_on, continues_on, when_all, bulk, sync_wait
  • Full scope suite (counting_scope, spawn, spawn_future) and coroutine task + task_scheduler
  • parallel_scheduler (P2079) — the standard system context
  • Requires C++23 (not C++20 like stdexec)

What it doesn't have:

  • Nothing beyond the spec: no when_any, sequence senders, type erasure, or GPU
  • No I/O — but bemanproject/net (P2762) is being built alongside

Watch this to track what will eventually land in the standard library. Spec-fidelity is the explicit primary goal.

Self-described: "under development and not yet ready for production use." Their clause-by-clause status doc shows implementation and tests essentially complete; review and docs still catching up.

bemanproject/net implements P2762 — sender-based networking, where standard async networking will come from. Early: only a poll(2) backend so far; io_uring / epoll / kqueue planned. C++29 target.

05
The Gap
The I/O problem
nobody talks about

The model is ready. The composition story is ready. The async I/O primitives most C++ engineers actually need day-to-day are not.

P2300 deliberately excludes I/O — here's what that means

Intentional, not an oversight. The authors scoped P2300 to the execution framework only. Concrete I/O is a separate layer to build on top. The proposal authors have always said networking and file I/O are C++29 territory.

What stdexec's io_uring integration actually is:

  • A scheduler that proves the wiring compiles and runs
  • Timers (async_wait) and stop propagation
  • The example in the repo only demonstrates cancellation flow
  • No async_read, async_write, async_accept, async_connect

GitHub issue #1062: "io_uring reading files." Filed 2023. The only response was a link to a separate external project. That's the current state.

What actually exists for sender-based I/O:

  • Asio + Leahy's stdexec adaptation — the only viable production path today. Asio has genuine async file I/O (stream_file, random_access_file) and network I/O, exposed as senders via Leahy's CppCon 2025 work. Requires Asio, and on Linux requires io_uring (BOOST_ASIO_HAS_IO_URING). Windows uses IOCP.
  • uring_exec — thin wrapper over every io_uring_prep_* op. Has read, write, accept, send, recv. Linux only. Research-grade.
  • maikel/senders-io — more designed file + network senders. Experimental, stale, old stdexec API.
  • Beman net (P2762) — the standards-track approach. Very early. C++29 target.
  • Intel bare-metal senders — P2300 subset for embedded/interrupt-driven I/O. No OS required.

If you're already using Asio and on Linux with io_uring — Leahy's adaptation work is the most complete sender-based I/O story available today. Everyone else is in DIY territory.

History, worth a beat: libunifex — the Facebook library P2300 grew out of — had working io_uring and epoll schedulers. That I/O coverage was deliberately left out of standardization scope. The gap didn't happen by accident; it was a scoping decision.

The platform picture is worse than it looks

Linux with io_uring best supported

  • io_uring is Linux-only (kernel 5.1+)
  • Community projects exist (uring_exec, maikel/senders-io, and my own fiberexec) — research-grade, not production
  • File I/O and network sockets both technically possible

Linux epoll / macOS kqueue DIY

  • No sender-based scheduler wrapping epoll or kqueue exists
  • You'd write your own — exposing completions as set_value()
  • Niebler's blog "What are Senders Good For?" is the guide

Windows IOCP nothing

  • No sender-based IOCP scheduler exists publicly
  • Asio wraps IOCP — so Leahy's Asio adaptation is the path for now

Embedded / bare-metal partial

  • Intel's bare-metal senders: a P2300 subset — interrupt-driven, no OS, no alloc
  • Shows the model generalizes to metal; separate library, not stdexec-interoperable

For raw socket users on any platform today: wrap your existing async layer to produce senders. The computation model is ready. The I/O layer is yours to bring.

The bridge: wrapping your existing async I/O as senders

If you have an io_uring scheduler, epoll loop, or any callback-based system — expose it as a scheduler today and gain composability without rewriting anything. I've done this integration in a research project, fiberexec: fibers inside, senders outside.

// Your existing C-style async API:
// void async_read(fd, buf, len,
//   void(*cb)(int result, void* ctx), void* ctx);

// Wrap it as a sender:
struct read_sender {
    using sender_concept = stdexec::sender_t; // C++26 final style
    using completion_signatures = stdexec::completion_signatures<
        stdexec::set_value_t(int),
        stdexec::set_error_t(std::error_code)>;
    int fd; char* buf; std::size_t len;

    template<stdexec::receiver R>
    auto connect(R receiver) {
        return read_op{fd, buf, len,
                       std::move(receiver)};
    }
    // Your ring's completion calls set_value(bytes)
    // or set_error(ec) on the receiver.
};

// Now your I/O flows into any sender pipeline:
auto work = read_sender{fd, buf, 4096}
          | stdexec::then(parse) | stdexec::then(process);

Niebler's blog "What are Senders Good For, Anyway?" (Feb 2024) walks this pattern in detail — wrapping a C-style async API to produce senders. Essential reading.

This is the practical adoption path right now for I/O engineers: keep your existing async I/O layer, expose it as a sender, gain composability at the computation level today.

When standard I/O senders eventually arrive (P2762, C++29+), you swap the wrapper for the standard primitive. The pipeline logic above doesn't change.

Before you wrap: two things to watch out for

Watch out: older stdexec examples and early P2300 talks use tag_invoke for customization — friend auto tag_invoke(connect_t, ...) etc. That mechanism was replaced in P2300R10, the final adopted revision. The C++26 standard uses plain member functions: connect(), start(), set_value(), and using sender_concept = sender_t. The code above reflects the correct final style.

Cancellation: wire the receiver's stop token into your layer's own cancellation so set_stopped() is real, not decorative — it's where hand-rolled wrappers cut corners. The actual flow inside fiberexec::run:

Narrate the U-shape: the stop request crosses the seam twice — down into the kernel as ASYNC_CANCEL, back up as set_stopped. That round trip is what "cancellation is real" means. This is fiberexec's verified flow (run.hpp + fiber_context.cpp), not pseudocode. Why ③ says "queued": the stop_callback runs on whatever thread called request_stop — not the ring's owner — and only the owning thread may touch the SQ ring. So request_cancel does a mutex-guarded queue push plus an eventfd write to wake the ring; the owning thread drains the queue into ASYNC_CANCEL SQEs on its next pass (ring-full handled: leftovers wait for the next wakeup). Bonus detail if probed: linked SQE chains cascade -ECANCELED; already-completed ops return -ENOENT and are discarded.

Adoption is workload-dependent

Compute-heavy async work

(parallel pipelines, GPU offload, CPU-bound task graphs)

  • stdexec's story is good here today
  • Thread pool + GPU schedulers are the most mature part
  • when_all, bulk, nvexec all work well in practice
  • Consider adopting stdexec now if you can tolerate API churn

HPC, scientific computing, GPU pipelines — this is the most compelling case for adoption today. The model was built for this use case first.

I/O-heavy async work

(network servers, file pipelines, embedded I/O, storage systems)

  • The composition model is sound and ready
  • The I/O primitives are not production-ready
  • Pragmatic path: wrap your existing async layer as senders
  • Use stdexec's async_scope for structured spawn patterns
  • Gain composability now; swap I/O layer when P2762 ships

As Leahy demonstrated at CppCon 2025 — don't rewrite, adapt. Your existing io_uring / epoll / socket code stays; the computation layer above it gains P2300 composability now.

Universal: Learn and experiment with stdexec on Godbolt now. Plan production adoption when libstdc++ or libc++ ships P2300 (likely 2–4 years). The concepts won't change even if the headers do.

This has strong endorsement — with a caveat

"std::execution is what I call C++'s async model — it provides a unified framework to express and control concurrency and parallelism… it also has important safety properties because it makes it easier to write programs that use structured concurrency and parallelism to be data-race-free by construction. That's a big deal."
— Herb Sutter, former WG21 chair (2002–2025), March 2026 London trip report

He also said: this feature is great but currently harder to adopt than most — it lacks great documentation and some "fingers and toes" libraries. Notably, his company (Citadel Securities) is already using it in production. He expects the gaps to close now that C++26 is done and attention turns to C++29.

What he didn't address: the I/O story for non-GPU, non-thread-pool workloads is genuinely thin right now. That's the gap your team needs to understand and plan around. It's a real limitation — not a reason to ignore P2300, but a reason to be clear-eyed about the timeline.

Summary

  • ▸Why: every pre-P2300 async codebase is correct but isolated — the standard gave us primitives, never a model.
  • ▸What: senders are lazy, composable descriptions of work; the scheduler is swappable — your io_uring ring can be one.
  • ▸The gap: C++26 is done, but no stdlib ships it (likely 2–4 years) — and P2300 deliberately excludes I/O.

  • ▸Verdict: learn now, plan carefully. Compute-heavy: adopt. I/O-heavy: adapt, don't rewrite.

The cost question (it will come): the default composed path is allocation-free — connect() builds a single operation state, typically on the stack; no type erasure, no ref-counting.
