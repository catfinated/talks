The Problem
What problem is this
actually solving?

The standard library gave us primitives. It never gave us a model. So we all built our own — and none of them compose.

The problem, concretely

Team A uses Boost.Asio for IPC. Team B uses threads and futures for CPU and GPU work. Team C uses threads and io_uring for file I/O.

You are asked to build the thing that uses all three: pull data off the network, process it, write the results to storage. Good luck.

  • ✗No two of them compose. Every pipeline across a boundary is a hand-written bridge — and a new one each time.
  • ✗None of them share a vocabulary. Each interface is its own; no generic algorithm can span them.
  • ✗Each invents error and cancellation propagation. Exceptions here, error_code there, silent drops somewhere else.

These aren't design mistakes — they're the ceiling any single-team library hits. Composing across teams needs a vocabulary everyone shares, and only a standard can provide one.

P2300's pitch: a vocabulary layer all three can speak. Work from any source composable with any other, through generic algorithms. It takes the instinct every one of those teams had — separate the computation from the execution context — and makes it universal.

Delivery: the ✗s are coordination failures, not engineering failures — no amount of skill fixes them from inside one team, because they require everyone else to agree on a vocabulary. Land that sentence before advancing; it's the whole reason the fix is a standard and not a better in-house library. Make it personal in the telling, not on the slide. You have built one of these three — say which as an aside, once. About Me already established it, so repeating it on screen was the duplication this slide used to have. "Good luck" should land dry. It is the only joke on the slide and it earns the three bullets that follow.

Why std::future isn't the model — and what is

What we already have

  • ✗No continuations. .then() was proposed in 2013 (N3721), shipped in the Concurrency TS in 2016, and never merged into the IS — chaining means blocking on .get() or spawning another thread.
  • ✗No cancellation, no readiness callback. You poll in a loop or you block.
  • ✗No scheduler control. std::async gives you one bit — new thread or lazy — and under the default policy even that bit is implementation-defined. You can never say which context.
  • ✗Blocking fan-in, one error channel. Join N futures serially. The only built-in failure path is set_exception, so an error_code I/O layer either throws system_error per errno, or smuggles results through expected<> and leaves the error channel unused.
  • ✗No ownership. A launched future is nobody's child. Drop it and the work runs on unwatched — there is no way to ask "is everything I started finished?"

What a real model needs

  • ✓Composable continuations. Chain, fan-out, fan-in — one syntax regardless of what's underneath.
  • ✓First-class cancellation. Stopped is its own completion channel, not an exception in disguise.
  • ✓Scheduler-agnostic. Thread pool, GPU, io_uring ring, interrupt handler — the computation shouldn't care.
  • ✓Uniform completion. Value / error / stopped, propagated automatically through the chain.
  • ✓Structured concurrency. Every async operation has an owner and none outlives it — RAII's discipline, applied to work in flight rather than memory.

Each ✗ maps to the ✓ beside it. One more requirement we'll meet in the model section: zero overhead on the default path — allocation opts in, never sneaks in.

This slide is the payoff for "I don't see how this is better than what we already have." The two column headings ARE the objection and the answer — what we already have, against what a real model needs. Say that connection out loud; the room heard the objection four slides ago and will not make the link on its own. Be precise if challenged on the error point — promise<expected<T, error_code>> obviously works, so don't say futures are "incompatible" with error_code I/O. The claim is that there's exactly one built-in failure channel and it's an exception: either you throw system_error for routine errno values, or you push failure into the value channel and the type stops telling anyone that failure is possible. And .get() rethrows wherever you happened to join, not where the error occurred. Further detail, if useful: futures always heap-allocate shared state, even for trivial work. launch::deferred is laziness without value — runs on the retrieving thread, can't target a scheduler, can't compose. jthread fixes thread lifetime but is still a thread: no when_all, no error propagation out. The coroutine ecosystem's failure modes are different — next slide.

What about coroutines?

C++20 gave us the coroutine mechanism — co_await and co_return — but almost no library to use it with. The problems below aren't with coroutines themselves; they're with the missing infrastructure around them.

  • ✗No standard scheduler — so no portability. cppcoro, Asio, folly, libunifex each reinvented where coroutines run. A coroutine written against Asio's executor doesn't compose with one written against your io_uring scheduler — so a library author cannot write one that works for both of you.
  • ✗No structured cancellation. Cancelling a coroutine chain requires library support — there's nothing in the language to propagate stop signals.
  • ✗Fan-out is awkward. co_await is sequential by nature; concurrent fan-out needs library primitives the standard doesn't have.

And one that isn't missing infrastructure: the frame. Elision is permitted, never required — and only fires when the coroutine is inlined and immediately awaited, not when the task is stored, passed or type-erased. A promise operator new controls where, never whether. A sender's operation state is in the caller's frame by construction: a guarantee, not a hope.

The good news: they interoperate

C++26 integrates them both ways: a coroutine task is a sender (P3552); any sender is awaitable via as_awaitable (P2300).

// Name the sender, then await it.
exec::task<int> my_coroutine() {
    auto doubled = stdexec::just(42)
                 | stdexec::then([](int x) { return x * 2; });

    co_return co_await std::move(doubled);
}

// A coroutine task is itself a sender
auto work = stdexec::when_all(my_coroutine(),  // sender ✓
                              other_work());   // sender ✓

Gotcha: co_await binds tighter than |. co_await s | then(f) awaits s and pipes the result into then. Parenthesize, or name it first.

On the allocation box, stay honest about scale: one frame per connection in a server is noise next to the socket — you'd reach for coroutines there without hesitating, and the appendix says so. It matters on a hot path measured in microseconds, which is exactly where this room lives. Don't turn it into "coroutines are slow"; the claim is narrower — it's an allocation you cannot forbid, only relocate. If challenged on HALO: the elision is real and both GCC and Clang do it, but it is an optimisation with no standard way to require it or to get a diagnostic when it fails. That asymmetry against connect() constructing an op state in place is the whole point. The takeaway to say, now that it is not on the slide: use co_await for sequential async steps where it reads well; use sender algorithms for parallelism, fan-out and scheduler control. Compose them freely. If asked how co_await on a sender actually works: task's promise has an await_transform that calls as_awaitable for you, which is why the code here needs no ceremony. In a coroutine whose promise does not handle senders, call stdexec::as_awaitable explicitly or build the promise on with_awaitable_senders. Both are P2300; the task type is P3552. The gotcha is worth 15 seconds: co_await is a unary-expression operator, so it outranks the pipe. The failure is usually a confusing type error, occasionally something that compiles and is wrong. Also note the std::move — these are single-shot senders and connecting from an lvalue is the wrong habit. Framing line before advancing: coroutines and std::future have DIFFERENT failure modes — futures fail at composability; the coroutine ecosystem fails at parallelism, cancellation, and portability. P2300 provides the missing infrastructure and treats coroutines as a first-class citizen in the process.

The model — three abstractions, three completions

No code yet. These are the only concepts the rest of the talk rests on.

The three abstractions

📍 Scheduler — a handle to an execution context. Where does work run? Your io_uring ring becomes one.

📦 Sender — a lazy description of async work. You spend ~95% of your time here.

📬 Receiver — a generalized callback. You almost never write one — but you'll call into one the moment you wrap your own I/O.

The three ways work completes — every operation ends on exactly one

set_value(args...)
Success. Zero or more values — a single completion can carry several independent results, which std::future cannot express at all.

set_error(err)
Failure. exception_ptr, error_code, or any type. Uniform propagation over the same channel, whatever the type.

set_stopped()
Cancellation. Structured and explicit — not an exception, not an error code.

And the property everything else follows from: senders are lazy values. Building a pipeline runs nothing — each step returns a new sender. Work starts only when a consumer connects and starts it. So a pipeline can be stored, returned from a function, passed to an algorithm, or handed to a scheduler its author never heard of.

If asked "so when WOULD I write a receiver?": separate consuming one from defining one. Wrapping I/O — the rest of this talk — means writing a sender and an operation state; connect hands you a receiver and you call set_value / set_error / set_stopped on it. You never define the type. You define a receiver type only when you write a sender ALGORITHM (then, or a custom adaptor), a custom consumer (your own sync_wait, spawning into your own scope), or type erasure like any_sender_of. If you're writing an adaptor you're extending the framework rather than using it — different talk. On the second block: pipeline() is a function returning a sender — that is the point. Because a sender is a value, the whole graph can be produced by a function parameterised on its scheduler, and the three call sites differ only in which scheduler they pass. Two minutes, not six. Read the three boxes in one breath — this room can define scheduler and receiver without help; the only lines that earn time are "your ring becomes a scheduler" and "you almost never write a receiver." Then land the hook: if your scheduler is an io_uring ring, pipeline(ring_sched) routes all that work through your ring and the computation logic is unchanged. That's the whole promise of the talk in one line. No code on this slide is deliberate — the vocabulary comes next, and the code after that. Everything here is a concept they need before a single algorithm name makes sense. The three completion channels pay off immediately: the next slide has one adaptor per channel.

The vocabulary to learn first

Thirty algorithms in C++26. These seven get you through almost everything — and three are just "read one of the completion channels."

Factories — make a sender out of something that isn't one

  • just(vals...)Completes immediately with the given values. The starting point when there's no scheduler involved.
  • schedule(sched)Completes on an execution context — the transition point. Everything piped after it runs there.

Adaptors — take one or more senders, return a new sender

  • then(sndr, fn)Reads the value channel. fn returns a value, which becomes the new value downstream.
  • upon_error(sndr, fn)Reads the error channel. Turns an error back into a value — recovery.
  • upon_stopped(sndr, fn)Reads the stopped channel. Turns cancellation into a value.
  • let_value(sndr, fn)Like then, but fn returns a sender — chaining a step that is itself async. let_error / let_stopped complete the grid.

Consumers — connect and start it. Nothing runs until one of these

  • sync_wait(sndr)Blocks until it completes. Returns optional<tuple<values...>> — empty on stopped, errors rethrow. Lives in std::this_thread.

Putting it together

Every algorithm here is one you just met.

// Nothing runs yet — this is just a description.
auto work = stdexec::schedule(sched)
    | stdexec::then([] { return compute(); })
    | stdexec::then([](auto r) { return transform(r); });

// Work STARTS here. This thread blocks until done.
auto [value] = stdexec::sync_wait(work).value();

One factory, two adaptors, one consumer. The pipe builds left to right; each step returns a new sender; sync_wait is the only line that does anything.

// A sender is a value — so make it a function of its scheduler
auto pipeline(auto sched) {
    return stdexec::schedule(sched) | /* ...same steps... */;
}

auto cpu_work  = pipeline(thread_pool_sched);
auto gpu_work  = pipeline(cuda_stream_sched);
auto ring_work = pipeline(io_uring_sched);  // yours!
// One adaptor per completion channel.
auto work =
    async_read(sched, fd, buf)      // might set_error()
    | stdexec::then([](Buffer b) {
          return parse(b);            // value channel
      })
    | stdexec::upon_error([](auto err) {
          log_error(err);              // error channel
          return fallback_value();
      })
    | stdexec::upon_stopped([] {
          cleanup();                   // stopped channel
          return fallback_value();
      });

Why auto err: then adds set_error_t(exception_ptr) unless the callable is noexcept — the handler has to take both.

No try/catch at every step. An error skips the rest of the value path and arrives at the first handler that reads that channel. Recovery puts it back on the value channel — which is why both handlers return the same type.

This is the first code in the talk, and everything in it was named one slide ago. Walk the left column top to bottom: build, nothing happens, sync_wait, now it happens. Then the pipeline() block — a sender is a value, so the whole graph can be a function of its scheduler, and the three call sites differ only in which scheduler they pass. That last line is the hook for the entire talk: swap in your io_uring ring and the computation is unchanged. The right column is the three channels, live — one adaptor each, in the same order they were introduced. Say why both handlers return the same type: recovery moves a completion back onto the value channel, so the types have to agree or sync_wait has two value signatures and rejects the pipeline. If someone asks about upon_stopped returning void: that gives the sender two distinct set_value signatures — legal, but sync_wait wants one. "Isn't then just the callback?"

The second objection I promised to come back to. Same operation, both ways.

The callback you'd have written

struct ctx { char* buf; };   // heap; free it yourself

void on_read(int result, void* p) {
    auto* c = static_cast<ctx*>(p);
    if (result < 0) { /* on whose thread?
                             report to whom? */ }
    else process(c->buf, result);
    delete c;
}

async_read(fd, buf, n, &on_read, new ctx{buf});
// nothing here to name, store, or compose

The sender

auto work = async_read(fd, buf, n)
          | stdexec::then(process);

// ...and `work` is a value:
stdexec::sync_wait(std::move(work));   // run here
scope.spawn(std::move(work));          // or there
co_await std::move(work);              // inside a task
stdexec::when_all(std::move(work),      // or fan out
                   other_work());

The consumer decides how it runs — not the algorithm. Same pipeline, four different executions, none of which async_read had to know about. spawn and when_all are coming up — that you don't know them yet is rather the point.

Where does the stop token go? There's one parameter left and it's void*. Same question for "which context does process run on?" and "who owns buf until completion?"

A callback is a function you give away. You hand it to async_read at the call site and it's gone. A sender is a value you keep.

The concession, and it's real: for one step, no errors, no cancellation, no fan-out — they are equivalent, and the callback version is less code. The value shows up at the second step, and at every seam between two libraries.

The two patterns that matter most

Fan-out with when_all

// Three operations run concurrently
auto work = stdexec::when_all(
    stdexec::starts_on(sched,
        async_read(fd_a) | stdexec::then(process)),
    stdexec::starts_on(sched,
        async_read(fd_b) | stdexec::then(process)),
    stdexec::starts_on(sched,
        async_read(fd_c) | stdexec::then(process))
)
| stdexec::then([](A a, B b, C c) {
    return combine(a, b, c); // after all three
});

No blocking between steps. No thread-per-operation. One clean join point. This shape is a graph — remember it when we get to whether senders are worth it for your workload.

Scheduler hand-off with continues_on

// Three schedulers, one pipeline.
async_recv(io_sched, socket, buf)      // on your ring

| stdexec::continues_on(gpu_sched)     // hand off
| stdexec::then([](Buffer b) {
      return process_data(b);       // runs on GPU
  })

| stdexec::continues_on(io_sched)      // back to ring
| stdexec::let_value([](Result& r) {    // fn returns a SENDER
      return async_write(io_sched, file, r);
  });

Swap CPU↔GPU and the control flow doesn't change. Errors and cancellation cross scheduler boundaries automatically.

Once sender-based async_recv / async_write exist this compiles as written; today you'd wrap your own io_uring layer to produce them. Structured concurrency — fire-and-forget, still owned

Every async operation has an owner, and no operation outlives it. The discipline scoped variables and RAII gave us for memory, applied to work in flight. async_scope is where you meet it.

// stdexec today
exec::async_scope scope;

scope.spawn(
    stdexec::starts_on(sched, do_work())
);
// caller continues immediately...

stdexec::sync_wait(scope.on_empty());
// ...but all spawned work is done here ✓
// C++26 — not just a rename
namespace ex = std::execution;
ex::counting_scope scope;

ex::spawn(ex::starts_on(sched, do_work()),
          scope.get_token());     // ← token

std::this_thread::sync_wait(scope.join());

spawn takes a scope token, not the scope — the algorithms are specified against a concept, so they work with any scope policy, including one you write. counting_scope is the policy the standard ships; simple_counting_scope is the same without stop support (P3149).

Forget to join and it calls terminate(). The destructor aborts unless the scope is joined, unused, or unused-and-closed. Correctness depends on remembering an idiom. Hold that thought.

spawn requires a sender that completes with no values — hence do_work() returning void. Need the result? That's spawn_future. And spawn is one of the few places the model allocates — by design.

If jthread comes up: std::jthread fixes the lifetime problem — genuinely useful — but it's still a thread: can't run on a scheduler, can't compose with when_all, can't propagate errors out. A jthread is a hammer; a sender scope is a grammar. If asked why a token rather than the scope: P3149 defines nest / spawn / spawn_future against the scope_token concept — copyable, with try_associate, disassociate and wrap — precisely so the set of scope policies stays open to user code and future standards. counting_scope is one policy, not the only possible one. Say "hold that thought" and mean it — the terminate box pays off two slides later on the destructor slide, and the callback is what turns a piece of trivia into the argument. Both scope types, if asked: counting_scope = simple_counting_scope + request_stop. Same state machine, same token machinery, identical destructors. If asked how faithful stdexec is here: exec::async_scope predates P3149 and the shapes differ — on_empty() vs join(), scope-as-argument vs token. Porting is mechanical but it is not sed. The point to land: spawn is where structured concurrency meets reality — you genuinely need unbounded fan-out sometimes, and this is the version that still lets you prove everything finished.

"Just do it in a destructor"

And the third — take it at face value and write the program it implies.

~BufferWriter() {
    // flush what's still pending before we go
    for (auto& b : pending_) {
        ::write(fd_, b.data(), b.size());
    }
}
  • ✗It has no idea why it's running. Success, error, cancelled — same code, no parameter. uncaught_exceptions() is the only signal, and cancellation isn't an exception: to a destructor, a cancelled operation is indistinguishable from a successful one.
  • ✗So it can't know whether flushing is even correct. After a failed or cancelled write, pending_ may hold a partial record. Writing it corrupts the file; dropping it loses data. It must guess.
  • ✗And it can't report either outcome — destructors can't throw, so a failed flush is silent.
  • ✗A blocking write on the shutdown path, with no timeout. Route it through your async layer and you're blocking on a context being torn down — the classic shutdown deadlock.
  • ✗And shutdown can't be parallelised. Objects are destroyed one at a time, in reverse order of construction — block scope, members, statics alike. Ten writers with 50 ms of I/O each is 500 ms of serial teardown that when_all would have finished in 50.

Three channels collapse into one. Everything the model keeps separate — value, error, stopped — arrives at ~T() as the same call. And the language forbids the fix: neither a constructor nor a destructor may be a coroutine ([class.ctor.general], [class.dtor]).

That is the thought I asked you to hold. counting_scope aborts because its cleanup is async and a destructor cannot be. A standard type whose correctness depends on an idiom — the C-style problem RAII was invented to kill.

The claim was that none of this matters. But every codebase that believes it ends up with a hand-rolled shutdown sequence, a comment explaining the ordering, and a bug nobody can reproduce.

The bridge: wrapping your existing async I/O as senders

If you have an io_uring scheduler, epoll loop, or any callback-based system — expose it as a scheduler today and gain composability without rewriting anything.

// Your existing C-style async API:
// void async_read(int fd, char* buf, size_t len,
//   void(*cb)(int result, void* ctx), void* ctx);

// Wrap it as a sender:
struct read_sender {
    using sender_concept = stdexec::sender_tag;
    using completion_signatures = stdexec::completion_signatures<
        stdexec::set_value_t(char*, std::size_t),
        stdexec::set_error_t(std::error_code),
        stdexec::set_stopped_t()>;  // you cancel — declare it

    int fd; char* buf; std::size_t len;

    auto connect(stdexec::receiver auto rcvr) && {
        return read_op<decltype(rcvr)>{fd, buf, len, std::move(rcvr)};
    }
};

// Now your I/O flows into any sender pipeline:
auto work = read_sender{fd, buf, 4096}
          | stdexec::then(parse) | stdexec::then(process);

This is the practical adoption path right now for I/O engineers: keep your existing async I/O layer, expose it as a sender, gain composability at the computation level today. This part is boilerplate — the next slide is where the heavy lifting happens.

Niebler's blog "What are Senders Good For, Anyway?" (Feb 2024) walks this pattern in detail — wrapping a C-style async API to produce senders. Essential reading.

When standard I/O senders eventually arrive (P2762, C++29+), you swap the wrapper for the standard primitive. The pipeline logic above doesn't change.

The operation state — where the real work lives

// using namespace stdexec; — elided below for width
template <stdexec::receiver R>
struct read_op {
    using operation_state_concept = operation_state_tag;
    read_op(read_op&&) = delete;      // pinned: built in place

    void start() & noexcept {
        // 1. hook the receiver's stop token into YOUR layer
        stop_.emplace(get_stop_token(get_env(rcvr_)), on_stop{this});
        // 2. submit; `this` is the completion context
        ::async_read(fd_, buf_, len_, &on_complete, this);
    }

    static void on_complete(int result, void* ctx) noexcept {
        auto& self = *static_cast<read_op*>(ctx);
        self.stop_.reset();          // unregister BEFORE completing

        if (result >= 0)
            set_value(std::move(self.rcvr_), self.buf_, std::size_t(result));
        else if (result == -ECANCELED)
            set_stopped(std::move(self.rcvr_));     // not an error!
        else
            set_error(std::move(self.rcvr_),
                      std::error_code(-result, std::system_category()));
    }

    int fd_; char* buf_; std::size_t len_; R rcvr_;
    using stop_cb_t = stop_token_of_t<env_of_t<R>>::template callback_type<on_stop>;
    std::optional<stop_cb_t> stop_;
};

Pinned, caller-owned storage. connect() constructs the op state in place and it never moves. This is where "no allocation on the default path" actually comes from — it isn't a slogan, it's this = delete.

Stop callback lifetime. The receiver carries an environment — a bag of queries the caller populates, which is how the stop token, scheduler and allocator reach you without appearing in any signature. Registered in start(), torn down before the completion fires. Get that ordering wrong and you have a use-after-free on the cancellation path — the bug that doesn't show up until production.

Three-way completion is the whole game. -ECANCELED maps to set_stopped, not set_error. Collapse those two and every upon_stopped downstream is dead code.

Slow down here — the pipeline syntax is familiar to this room; the seam is what's worth their time. Three beats: pinned storage (the zero-overhead claim made concrete), stop-callback ordering, three-way completion.

Why reset() comes first — and it is NOT about double completion. The kernel gives one CQE per SQE; you cannot be completed twice. Two real hazards. (1) A stop-callback destructor blocks until a concurrently-running callback returns. Resetting first is your only synchronisation with an on_stop that may be executing on another thread right now — the thread that called request_stop. (2) set_value propagates outward and the whole nested op state is often destroyed inside that call: sync_wait returns, the parent completes, a loop re-emplaces the state. After it returns, self may not exist. So touch nothing afterwards. The rule, in one line: completing is the last thing your operation state does — not the last interesting thing, the last thing. Finish all your business first (unregister, move the result out), then complete, then return. Assume destroyed rather than "is destroyed": whether it dies inside the call depends on the consumer — sync_wait tears it down, a scope destroys a spawned op, repeat_until re-emplaces it — and being generic over R means you cannot know which one you are connected to.

The stop_cb_t line is the one people cannot guess. You need the receiver's own stop-token type, reached through its environment — not std::stop_callback, because in-place stop sources are the common case and hard-coding std::stop_callback reintroduces the shared-state allocation. Idiom is straight from stdexec; the template keyword is required because R is dependent.

If asked: · where's the constructor? the deleted move ctor makes read_op a non-aggregate, so the previous slide's brace-init needs a real one, elided for space. Don't pretend it compiles as printed. · the environment — read_env pulls a query out, write_env overlays entries for a child, unstoppable is write_env with a token that never fires; it's how spawn finds its allocator and affine its scheduler, with no parameter anywhere. · exactly-once completion is guaranteed by the sender/receiver protocol, not by structured concurrency — structured concurrency is built ON it, since you can't join N children that might complete twice or never. Don't let anyone reverse that. · why connect is &&-qualified — single-shot senders; connecting from an lvalue is how you submit the same op twice.

Adoption is workload-dependent

Compute-heavy async work

(parallel pipelines, GPU offload, CPU-bound task graphs)

  • stdexec's story is good here today
  • Thread pool + GPU schedulers are the most mature part
  • when_all, bulk, nvexec all work well in practice
  • Consider adopting stdexec now if you can tolerate API churn

HPC, scientific computing, GPU pipelines — this is the most compelling case for adoption today. The model was built for this use case first.

I/O-heavy async work

(network servers, file pipelines, embedded I/O, storage systems)

  • The composition model is sound and ready
  • The I/O primitives are not production-ready

Starting from scratch? Senders are not the go-to yet — you'd be building the I/O layer and the wrapper, and the standard gives you neither. Put senders above it if you need composability with the compute layers; inside it, use senders, coroutines, callbacks — whatever fits.

Already have an async I/O layer? Expose it as senders and you get the whole model — structured cancellation, uniform completion, scopes — plus composability with every other sender-shaped library. The io_uring / epoll / socket code underneath doesn't change.

Sharper test than compute vs I/O — is your async work a graph, or a chain? Fan-out, joins, work crossing a ring and a pool and maybe a GPU: that's a graph, and the algebra earns its complexity. Read a frame, parse it, write a response: that's a chain, and a coroutine expresses it with far less machinery. Most I/O-heavy systems are some of both — the seam is where you decide.

If you already own an async I/O layer, wrap it behind a sender-shaped seam. That is the recommendation, it pays off today, and it survives whichever way the standard lands. How much you build on top of it is what depends on your workload.

Appendix A · reference for Q&A — not presented live

"Could I write a network server with this?"

First, a terminology trap. Single-shot vs multi-shot is about how many times a sender can be connected — not how many values it delivers. just(42) is multi-shot because it's copyable; a coroutine task is single-shot; exec::split converts one to the other (cut from C++26 by P3682; a stdexec extension now). Every sender completes exactly once. Multi-shot is not "recv until the peer closes."

Streams need a different abstraction: sequence senders. One emits many items via set_next before a final completion. stdexec has them in exec/sequence/ — iterate, transform_each, ignore_all_values, merge_each.

Not in C++26. No paper. Nothing in Beman. I'm told they are actively being worked on.

Don't confuse these with std::execution::sequence (Leahy's P4320, based on exec::sequence) — that runs senders one after another. Sequential composition, not streaming. The naming is unhelpful.

The lifetime story is ready. A server's fan-out is unbounded and runtime-determined — N connections, each outliving the accept iteration that made it. That is what counting_scope exists for: spawn each connection through scope.get_token(), keep accepting, shut down with request_stop() then join().

Three ways to write the loop today

  • ▸Coroutine per connection. An exec::task with an ordinary while loop over co_await async_recv(...). Readable by anyone; one frame allocation per connection, which is noise next to a socket. What I'd reach for.
  • ▸repeat_until — the loop in pure sender form. (Was repeat_effect_until; that spelling is now deprecated.) Pitfall: it needs the sender to be either copyable or lvalue-connectable, which type-erased senders generally aren't. Erase a sender factory instead.
  • ▸Sequence senders — accept_seq | transform_each(handle) | ignore_all_values. Experimental; open bugs include type-erased sequences not propagating stop tokens.

"Static pipelines only" is half wrong. The types are static and monomorphized; the graph is not. let_value picks the next sender at runtime, spawn gives runtime child count, any_sender_of erases shape, coroutines give arbitrary control flow. The dynamic parts cost a frame or an erasure allocation — the zero-allocation property covers the statically-shaped parts only.

Paper status, confirmed with the author: P3955 now has an R1 carrying wording — SG1 saw R0 at Brno, liked it, and asked to see it again with wording. That is real forward motion; say "in front of SG1 with wording", not "coming in C++29". P4320 has an R1 as of 2026-08-22, a wording bug fix only. Naming, verified against a recent checkout: repeat_effect_until is deprecated — <exec/repeat_effect_until.hpp> warns and forwards to <exec/repeat_until.hpp>, and repeat_effect_t / repeat_effect_until_t are [[deprecated]] aliases for repeat_t / repeat_until_t. Current spellings: exec::repeat, exec::repeat_until, exec::repeat_n. The naming trap, worth stating plainly: std::execution::sequence (P4320) runs senders one after another — sequential composition. Sequence SENDERS are the stream abstraction, they are very experimental, Kirk Shoop is actively working on them and Dietmar Kühl reportedly plans to. Two different things with confusingly similar names; do not let the room conflate them. The honest verdict, if asked outright: the lifetime and composition story is ready; the stream story is not, and there's no socket to accept from in the first place — which is the thesis of the whole talk. Today you'd use Asio through asioexec for real accept/recv/send senders and coroutines for the per-connection loops. Lead with the terminology correction — most people asking this question have conflated multi-shot with multi-value, and clearing that up answers half the question before you get to the rest. Don't oversell counting_scope: it solves connection lifetime, not streaming. Two different gaps.

"Can I build the graph at runtime, from a config file?"

Yes — and the shape of the answer is the same as every other dynamic-shape question. It works; you pay for it at each dynamic edge.

// One erased vocabulary type for every node kind
using node = exec::any_sender_of<
    set_value_t(Frame),
    set_error_t(std::error_code),
    set_stopped_t()>;

// kind -> factory, populated at startup
std::map<std::string,
         std::function<node(Params const&)>> registry;

node build(YamlNode const& cfg) {
    node s = registry.at(cfg.kind)(cfg.params);
    for (auto const& child : cfg.children)
        s = std::move(s) | then(adapt(child));  // re-erased
    return s;
}

What each dynamic edge costs. An allocation — the op state's size is no longer known — and no inlining across the seam. Every node kind must share one completion signature set.

The compile-time contract stops helping. Signatures were checked while the graph lived in the type system; a YAML-driven graph moves those errors to runtime.

Runtime-N fan-out needs a different tool. when_all is variadic — compile-time arity — and stdexec has no when_all over a vector. Spawn each branch into a counting_scope and join, or collect spawn_future results. Also: erased senders aren't copyable, so repeat_until rejects them — erase a factory instead.

The alternative: codegen. Emit the pipeline as C++ from the config at build time and everything stays monomorphized.

The fair comparison isn't against static senders — it's against what you'd pay anyway. A config-driven graph in a callback or virtual-dispatch design costs an indirect call and an allocation per node too. Senders aren't worse here; they just aren't better, because you've opted out of the thing that makes them fast.

Lead with the concession, not the mechanism. "Yes, and here's the honest cost" plays much better than walking the code first — the questioner usually already suspects there's a catch. The line that matters: you've opted out of monomorphization, which is where the performance came from; that is a property of the requirement, not of senders. If they push on the type-system loss: that one is real and worth conceding fully — compile-time completion-signature checking is a selling point of the model, and a runtime-assembled graph throws it away. Codegen is the answer that keeps both, and it is worth mentioning even though it is more build machinery. Verified: stdexec has no when_all over a runtime-sized range; when_all is variadic. counting_scope + spawn + join is the practical runtime-N fan-out.

What "in the caller's frame" actually means

connect() builds one object. Each adaptor's operation state contains its child's — so the whole pipeline is a single nested value with a size known at compile time.

stdexec::sync_wait(
    async_read(sched, fd, buf, len)
  | stdexec::then([](char* p, std::size_t n) {
        return std::string{"hello "}
             + std::string{p, n};
    }));

Two senders, one object, zero allocations. Its size is the sum of the boxes on the right, fixed at compile time.

This is why the op state is immovable: the outer state holds the inner one by value. Move it and every stashed pointer — including the one the kernel is holding — dangles.

Appendix slide — pull it up if someone asks what the operation state actually looks like, or doubts the zero-allocation claim. The innermost box is read_op from the wrapping section, which is why it uses async_read rather than a toy: they have already seen start() and on_complete(), and this shows where it lives. The recursive rule, if you state one thing: every operation state holds the receiver it will complete, whatever its own algorithm needs, and its child's operation state. That rule generates the entire picture. Walk it outside-in: sync_wait's state holds then's, which holds yours — each by value, not by pointer. Note whose receiver is where: read_op's rcvr_ is NOT sync_wait's receiver — it is one then manufactured, pointing back at then's op state. Completions climb that chain outward. In stdexec these inner receivers are lightweight wrappers over a pointer to the enclosing op state, not fat objects, so the nesting costs less than the boxes suggest. sizeof the whole thing is the sum, known at compile time, sitting wherever the caller put it. The line worth saying slowly: the SQE's user_data points into the middle of this object, which is why moving it would be catastrophic and why the move constructor is deleted. The previous slide's rule becomes this slide's picture. Say the two directions: connect nests inward, completions propagate back out. That counter-flow is the shape of the whole model. Note set_value carries two values — buffer and length — which is the multi-value capability from the model slide, in real code. std::future cannot express it. If asked what breaks the guarantee: type erasure (size stops being known), spawn (the scope must own the state), coroutine frames. All three are the dynamic-shape cases from the appendix; this holds for the static shape. It turns the = delete into a picture — that is the fastest way to answer "how is there no allocation?"
Appendix D · reference for Q&A — not presented live

then vs let_value

The whole rule: then's callable returns a value; let_value's returns a sender. Reach for let_value whenever the next step is itself asynchronous.

then — synchronous transform

just(x) | then([](int x) {
    return x * 2;      // a value ✓
});
// downstream sees: set_value(int)

Runs on whatever context the previous step completed on. No new async work is introduced.

let_value — chain in async work

just(path) | let_value([&](string& p) {
    return async_read(sched, p);
    // ↑ a sender ✓
})
| then([](Buffer buf) {
    return parse(buf);
});

The returned sender is connected and started; the pipeline's completion is its completion. This is how you nest one async operation inside another.

The common mistake: using then with a callable that returns a sender. It compiles — and gives you a value completion carrying an unstarted sender that nobody ever connects. The work silently never runs.

Pull this up if someone asks for the distinction in code. The failure mode in the red box is the one worth saying out loud — it's the quiet bug, not a compile error, and everyone hits it once. Why the parameter is an lvalue reference: let_value stores the predecessor's values in the operation state and keeps them alive for the duration of the returned sender — so the callable is invoked with lvalues. Taking by value copies for no reason, and fails outright for move-only types. then is different: its result is moved downstream immediately, so by-value there is fine.
Appendix E · reference for Q&A — not presented live

Structured concurrency — safety by construction

The old way — danger

// Thread may outlive `data`
std::thread([&data] {
    process(data); // dangling ref! 💥
}).detach();
// data destroyed here

Detached threads are a well-known footgun. No way to know when — or whether — they complete.

The sender way — safe

// Work is nested — cannot outlive scope
stdexec::sync_wait(
    stdexec::starts_on(sched,
        stdexec::just(data)
        | stdexec::then(process)
    )
);
// Guaranteed: process() is done here ✓

The detached-thread comparison sits below this room's level, which is why it is in the appendix — it is here for the case where someone wants senders contrasted with raw threads directly. This is the slide that owns the term — senders and structured concurrency get named together constantly, and the deck uses the phrase on half a dozen slides, so define it once, here, out loud: every async operation has an owner, and none outlives it. Same discipline as RAII, applied to work rather than memory. Don't overclaim this one: a counting_scope you never join is still a bug, and you can still write unstructured code by hand. What changed isn't a guarantee, it's that the committee took the easy detach out of the standard before it shipped — that's a fact about their behaviour, which is a stronger thing to say than a promise about yours. If jthread comes up: std::jthread fixes the lifetime problem — genuinely useful — but it's still fundamentally a thread: can't run on a scheduler, can't compose with when_all, can't propagate errors out. A jthread is a hammer; a sender scope is a grammar. And yes, you can still misuse the low-level primitives — the high-level API steers you away from it.
